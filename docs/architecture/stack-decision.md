# 技术栈决策

更新日期：`2026-06-07`

## 1. 决策范围

由于本项目已从研究阶段进入可运行的实现阶段，本文档记录了第一阶段（Phase 1）的技术栈决策。

## 2. 决策摘要

已实现的第一阶段路径：

1. 应用层：定制的 Python 本地 HTTP 服务
2. 模型访问模式：兼容 OpenAI 的 `/chat/completions` 接口
3. 提供商选项：托管 API、Ollama、LM Studio、vLLM 或兼容的网关
4. 首个批量数据集目标：CMMLU
5. 更广泛的验证索引：CMMLU 加上 AGIEval MCQ
6. 外部客户端目标：调用 `/ocs/query` 的 OCS 风格源配置

## 3. 为什么这是最佳起点

### 3.1 为什么首先使用定制服务

- 对 OCS 响应和处理器结构进行精准控制
- 避免在浏览器端暴露模型的 API 密钥
- 减小 Windows 环境下的安装面
- 直接使用规范化的 JSONL 题目索引
- 更容易针对最终配置驱动流（config-driven flow）进行自动化验收检查

### 3.2 为什么使用兼容 OpenAI 的提供商抽象

- 保持模型层可切换
- 避免将系统锁定在单一运行环境中
- 目前可配合托管 API 工作，后续可无缝切换到本地运行环境

### 3.3 为什么可以先使用云端 API

- 验证速度更快
- 本地设置摩擦更小
- 在调试本地推理质量之前，帮助我们评估检索质量

### 3.4 为什么首先选择 CMMLU

- 已在本地可用
- 直接的 CSV 结构
- 明确的非商业许可证声明
- 广泛的学科覆盖率

## 4. 何时应倾向于定制后端

本项目已选择定制 Python 后端，因为以下需求是迫切的：

- 超出平台支持的自定义排序逻辑
- 复杂的源融合规则
- 严格的本地数据处理，不依赖第三方平台
- 从第一天起就必须严格控制的自定义导出契约

MaxKB、FastGPT 或 Open WebUI 仍可在后续作为可选的管理或导入层进行评估，但对于当前的 OCS 就绪（OCS-ready）服务而言，它们并不是必需的。

## 5. 本决策未锁定的内容

本决策未锁定：

- 最终的模型供应商
- 长期来看是使用本地还是托管的推理
- 最终的 UI 层
- 后续是否添加自定义导入或检索微服务

## 6. 第一阶段定义

当满足以下条件时，第一阶段即告成功：

- 可导入受信任的数据集
- 可查询规范化的题目
- 系统返回答案、解析和出处
- 低置信度的结果被清晰标记

当前状态：第一阶段已实现，并通过了本地和模拟模型检查的自动化验收。

## 7. 当前开放性问题

这些问题并不阻碍第一里程碑的代码编写：

- M3KE 许可证条款是否可以确认
- 完整 C-Eval 数据载荷是否可以从当前环境获取
- AGIEval 应该用于检索还是仅用于评估
