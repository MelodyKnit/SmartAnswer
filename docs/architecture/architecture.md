# 架构设计

更新时间：`2026-06-07`

## 1. 目标

本项目需要一个可靠的、面向学习的检索服务，该服务接收规范化的题目输入，检索维护的题库，（可选地）调用大模型对答案进行规范化或解释，并返回包含来源归属的结果，供用户进行审核。

## 2. 设计原则

- 检索优先，生成次之
- 在客户端专属适配器之前，建立稳定的规范化 API
- 每一个答案路径均保留来源归属
- 可插拔的模型提供商
- 可插拔的数据导入管道
- 职责单一且可测试的服务边界

## 3. 推荐的高层架构

```text
题目输入
  -> 输入规范器 (Input Normalizer)
  -> 检索门面 (Retrieval Facade)
     -> 精确/关键词匹配器
     -> 向量/混合检索器
     -> 外部源适配器（可选且受控）
  -> 证据排序器 (Evidence Ranker)
  -> 答案组合器 (Answer Composer)
     -> 直接答案解析器
     -> LLM 解释策略
     -> 受信任的 AI 答案缓存
  -> 响应格式化器 (Response Formatter)
  -> HTTP API
```

## 4. 主要组件

### 4.1 输入规范器 (Input Normalizer)

职责：

- 验证传入的负载
- 规范化题目文本
- 规范化选项列表和题目类型
- 生成规范的检索查询

输入：

- 题目 (title)
- 选项 (options)
- 类型 (type)
- 可选的元数据，例如学科、来源、标签、语言区域 (locale)

输出：

- 规范化的题目负载
- 规范的搜索键值
- 缺少必填字段时的验证错误

### 4.2 检索门面 (Retrieval Facade)

职责：

- 暴露一个内部检索入口点
- 屏蔽答案是来自精确匹配、混合 RAG 还是可选的外部源

推荐模式：

- `Facade`（门面模式）：提供单一稳定的服务边界
- `Strategy`（策略模式）：提供可互换的检索方法
- `Adapter`（适配器模式）：用于适配 API 不一致 of 外部系统

子功能：

- 题目标题精确匹配
- 题目标题模糊匹配
- 结合选项重排
- 针对分块知识的向量检索
- 具有清晰出处的外部源查询（可选）

### 4.3 证据排序器 (Evidence Ranker)

职责：

- 对候选证据进行评分
- 相比于仅靠模型的大胆猜测，更倾向于采用精心整理的题库条目
- 综合考虑标题相似度、选项重合度、题目类型兼容性以及来源可信度

推荐评分顺序：

1. 整理好的问答（QA）精确匹配
2. 整理好的问答（QA）模糊匹配（结合选项支持）
3. 重合度高的受信任 RAG 片段
4. 经过多次一致性验证后晋升的受信任 LLM 缓存条目
5. 具有可验证出处的外部源结果
6. 仅靠模型的兜底回答

### 4.4 答案组合器 (Answer Composer)

职责：

- 决定是否可以直接从证据中返回答案
- 当本地证据缺失时，仅复用受信任的已缓存 AI 答案
- 仅在需要规范化、解释或消除歧义时才调用 LLM
- 强制要求结构化输出

输出预期：

- 候选答案
- 解释
- 来源列表
- 置信度
- 解析模式，例如 `exact_match`、`retrieval_match`、`llm_normalized` 或 `fallback`

### 4.5 响应格式化器 (Response Formatter)

职责：

- 将内部响应映射为稳定的外部 JSON 契约
- 同时保留便于机器处理的字段和便于人工审核的字段

## 5. 提供商抽象 (Provider Abstraction)

模型层不应与任何单一的运行时耦合。

推荐的提供商契约：

- `chat(messages, options) -> 结构化结果`
- `embed(texts) -> 向量`
- `health() -> 提供商状态`

推荐的提供商实现：

- 兼容 OpenAI 的云端 API
- Ollama
- LM Studio
- vLLM

为什么这很重要：

- 项目可以从云端 API 开始，随后以极低的代码改动成本切换到本地推理
- 当底层的模型端点兼容 OpenAI 时，MaxKB 和 FastGPT 都能很好地工作

## 6. 数据存储模型

### 6.1 规范化题目记录 (Canonical Question Record)

需要保留的字段：

- `question_id`
- `title_raw`
- `title_normalized`
- `question_type`
- `options_raw`
- `options_normalized`
- `answer_raw`
- `answer_normalized`
- `explanation`
- `subject`
- `chapter`
- `tags`
- `source_name`
- `source_url`
- `source_license`
- `ingest_batch`
- `created_at`
- `updated_at`

### 6.2 检索索引视图

为以下内容维护独立的视图：

- 精确匹配文本索引
- 模糊/关键词索引
- 向量索引
- 出处和许可元数据

## 7. 已初始实现的架构栈

当前实现：

- 后端：由 uvicorn 运行的 FastAPI 服务
- 索引：位于 `data\normalized` 下规范化的本地 JSONL 文件
- 检索：精确匹配优先，模糊匹配次之
- 模型提供商：兼容 OpenAI 的聊天补全（chat completions）适配器
- AI 学习库：位于 `data\normalized\ai-learned.jsonl` 的统一 JSONL 学习库，只有在多次高置信度一致后才会晋升
- 外部客户端适配器：支持 OCS 风格的 `/ocs/query` 响应和数据源配置

当前已实现的运行流程：

```text
本地精确匹配
  -> 直接答案规则
  -> 受信任的 AI 学习库匹配
  -> 本地模糊匹配
  -> 模型兜底
     -> 在模型回答前进行可选的网页搜索
     -> 搜索成功时，返回基于证据的模型回答
     -> 搜索无证据时，返回纯模型回答
```

这是当前的基线行为。请勿与更严格的未来策略（如“模型优先，仅在不确定时进行搜索”）混淆，因为该流程尚未实现。

为什么这是正确的首选架构栈：

- 它直接匹配了所需的 OCS 配置工作流
- 它避免了在浏览器端配置中放入模型 API 密钥
- 它既适用于云端 API，也适用于本地模型运行时
- 它在每个答案路径中都附带了来源归属和审核元数据

## 8. 可选的未来产品技术栈

### 方案 A：更快速的产品导向路线

- 应用层：`MaxKB`
- 模型端点：优先采用兼容 OpenAI 的云端 API
- 后期本地替换：`Ollama` 或 `vLLM`
- 种子数据：整理好的 QA CSV/XLSX

原因：

- 知识库管理和应用 API 已然存在
- 支持离线文件、表格、QA 对和网站知识源
- 支持兼容 OpenAI 的应用 API

### 方案 B：更偏向工程导向的路线

- 后端：Python 服务
- 存储：PostgreSQL + pgvector
- 嵌入/重排/模型：兼容 OpenAI 的提供商
- 导入：CSV/XLSX/JSON 管道

原因：

- 具有最高程度的长期自主控制权
- 如果自定义评分和自定义导出比管理 UI 更重要，这是最佳选择

## 9. 可靠性控制

服务不应在没有出处元数据的情况下返回纯答案。

最低限度的控制：

- 置信度评分 (confidence score)
- 来源列表 (source list)
- 解析模式 (resolution mode)
- 检索追踪 ID (retrieval trace id)
- 导入批次 ID (ingest batch id)
- 针对模型和检索依赖项的健康检查

推荐的运维检查：

- 导入期间记录的来源许可
- 导入期间的重复项检测
- 导入的模式（schema）验证
- 当模型处于猜测状态时，明确标记兜底标识

## 10. 避免过早耦合

请勿强耦合：

- 客户端适配器逻辑与核心检索逻辑
- 一次性的外部源解析器与规范的存储模式
- 模型提示词与传输层请求处理
- 仅限本地的运行时假设与提供商接口

## 11. 开发就绪度

核心实现已经就绪。后续开发应侧重于：

- 真实的 OCS 客户端验证
- 真实的云端或本地模型端点验证
- 引入更多获得许可的来源数据
- 如果有需要，可通过结合选项的评分或向量检索来强化检索能力
