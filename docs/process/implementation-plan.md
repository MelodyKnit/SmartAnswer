# 实施计划

更新时间：`2026-06-07`

## 1. 锁定的决策

首个实施路径已锁定：

1. 平台：自定义的 Python 本地服务
2. 模型提供商：兼容 OpenAI 的端点
3. 首个经验证的数据集：CMMLU
4. 更广泛的经验证数据集：CMMLU 加上 AGIEval MCQ
5. 规范导入格式：采用 `CanonicalQuestionRecord` 结构的 JSONL 记录

做出此决策的原因是，最终所需的用户工作流是一个调用固定本地服务端点的 OCS 风格配置。

## 2. 为什么首选兼容 OpenAI 的提供商是合理的

使用兼容 OpenAI 的 API 边界能够带来：

- 直接支持托管的云端 API
- 直接支持本地运行时，例如 Ollama、LM Studio 或 vLLM
- 无需在 OCS 配置中暴露 API 密钥
- 统一的提供商契约，用于兜底和解释生成

在以下情况下使用云端 API：

- 相比于仅限本地运行，更看重答案质量
- 本地硬件配置有限
- 用户想要快速进行验证

在以下情况下使用本地运行时：

- 隐私需求增加
- 使用量过大导致托管成本过高
- 模型栈需要完全的离线控制

## 5. 投入生产前的验证关卡

- 导入的数据通过 schema 验证
- 每次成功的返回结果均包含出处信息
- 低置信度的响应带有相应标记
- 提供商健康检查端点保持稳定
- 经过人工审核的评估样本满足约定的阈值

## 6. 评估样本设计

使用三个测试组：

1. 精确匹配的精选题目
2. 答案相同但表述不同的题目
3. 措辞相似但干扰项较多的题目

追踪指标：

- Top-1 答案准确率
- 来源命中率
- 解释的有用性
- 虚假置信度比率

## 7. 早期需要关注的风险

- 在 schema 稳定前导入大量嘈杂的数据集
- 在检索未命中时过度依赖模型的猜测
- 混合不同来源许可且未做好记录
- 过早地将客户端映射逻辑与后端设计相耦合
- 在了解基线质量之前就采用本地推理

## 8. 当前开发清单

在完成以下工作后，项目即可进行真实环境的验证：

- 在目标端口上启动服务
- 如果需要大模型兜底，选择真实的大模型端点
- 在用户实际的客户端中加载 OCS 配置
- 确认用户脚本对 `127.0.0.1` 或 `localhost` 的连接访问权限
